Open Source Summit + Embedded Linux Conference Europe 2026 (Prague) report and presentation notes

Finally I sufficiently edited my notes for a little belated post on the Open Source Summit + Embedded Linux Conference Europe 2026 in Prague. I was quite excited to attend as it was my first conference/summit, and it certainly delivered. Organizationally, it was handled very well, and there were always plenty of presentations, booths, and activities to attend. The schedule was also planned in such a way that coming up to the booths to talk about projects (which ranged from things like Flatcar container Linux to RISC-V automotive projects and many, many more across the entire open source and embedded space) in-between some talks and during breaks was generally feasible, so over the course of the several-day conference you could visit most if not all of them.

Below I will provide a non-exhaustive list of talks I attended with corresponding notes. I didn't write notes for all of the talks and keynotes I attended, so this list is partial, yet still mostly complete.

October 7th

Triaging CVEs for the Linux Kernel - Christoph Steiger & Negar Masoudifar, Siemens AG https://hosted-files.sched.co/osselceu2026/79/triaging-cves-for-the-linux-kernel.pdf

  • rising number of cves in 2026 (in part due to agentic explosion)
  • on average every bug once per 7 days in 2026
  • updates not always possible (espesially in embedded with various ctrict certifications)
  • maintaining your own kernel fork is too much effort, many companies tried it, many abandoned the idea
  • LTS is the way to go for the most part
  • presented tool: kernel-cve-triage
  • check CVE commit and fixing commit in version history
  • find affected config opts with kmax

If you’re not building the file and you never build it – it doesn’t affect you – around 5-10% functionality of the kernel may actually be used in the build (personal note: similar to how our usage of brain capabilities is limited compared to its potential).

  • kmax helps determing from a file which config options we need to set
  • the presented tool takes 1-2 secs per CVE, mostly due to expensive git history lookups
  • next: comparison with yocto CVE check
  • yocto starting point: CVE -> check whether version is affected or not -> build the kernel, extract include files from debuginfo during building, check if affected files are built
  • minor difference: yocto needs to build the kernel to extract info, while the presented tool just needs the source tree to determine the affected files and configs, no need for building empirical comparison or same kernel version and same config:
  • patched and unpatched classification: tools are similar
  • main difference: ignored category
  • reasons: file determination can fail
  • kmax sometimes fails to determine the relevant config

Shown approaches filter around 80 percent of CVEs, likely it’s the ceiling possible. Auhors suggest adding affected Kconfig in vulnerability reports (kernel CVEs), use LTS and SLTS (Super LTS), join communities like CIP.

Relevant links: https://cip-project.org/ https://gitlab.com/cip-project

Reproducible Embedded Linux Testing From Laptop To CI To Scale - Anders Roxell, Linaro https://hosted-files.sched.co/osselceu2026/32/Reproducible%20embedded%20linux%20testing.pdf ARM CCA on QEMU * OP-TEE on QEMU and RPI 4

  • OP-TEE and CCA are not one project
  • OP-TEE: TF-A, OP-TEE, u-boot, linux …
  • CCA: TF-A, TF-RMM, EDK2, Linux/kvm, qemu, guest/rootfs

Then there is FVP (ARM virtualization platform)

Overall: tuxmake (linux( tuxfirmware (tf-a, op-tee, userspace) tuxuboot (u-boot) shrinkwrap (CCA) → artifacts → tuxrun (qemu, fvp, board) https://github.com/kernelci/tuxmake

local: python command, local/url files, build/test locally: cloud: yaml…

Overall I felt like the talk didn't really get its point across (at least to me) and was a bit confusing with its pacing. It ended 20 mins before schedule with no questions so maybe it's not just me who was a bit bamboozled :)

Keynote: Open Source at a Crossroads: Geopolitics, Sovereignty, and the Fight to Stay Open - Nithya Ruff, Chair, Linux Foundation Board & Johan Linaker, Senior Researcher, RISE Research Institutes of Sweden & Adjunct Assistant Professor, Lund University

Central point: open source enables govs to collaborate even with rivalry present; industry learned the lesson: open source their own code, co-invest in shared projects and solve problems. Should govs do the same?

In the end there was a list of sovereign AI projects by country (not exhaustive of course): Teuken, llm-jp, openeurollm, aperitus, sea-lion.

Personally I think collaboration would of course ease up tensions, but we should account for the fact that some govs may use others' open source advancements for their own malicious goals while not really sharing their own achievents. So there is a bit of a game-theoretic problem here.

Kata at Scale: The Hidden Cost of Running VMs Behind Every Container - Kavitha Daula & Nigel Douglas, Edera https://osselceu2026.sched.com/event/2RaXe/kata-at-scale-the-hidden-cost-of-running-vms-behind-every-container-kavitha-daula-nigel-douglas-edera

Edera is supposedly an alternative to Kata as a full-fledged platform. The presenters describe their experience and troubles with kata containers. Specifically, kata adds lots of complexity due to its architecture compared to “just containers" (true enough). You now have to manage a ton of stuff regarding the guest kernel – it’s part of the workload. Performance, modules, CVEs, etc. That is, the kernel is no longer infrastructure, it’s production artifact. If you add confidential containers (note: e.g. CoCo, EdgelessSystems Contrast, etc) to that, it becomes even more complex.

Some personal note: while the listed problems are true, I don't think they're necessarily a strong enough argument against Kata - I mean, everything today is so complex, so what's another convoluted project to manage, right? Although I can actually add even more examples that make Kata harder to use - for instance, while with "just containers" like Docker, Podman, cri-o, etc we have a rather established software stack for monitoring, tracing, observability of containers, we don't really have that with Kata, and what we do have is very limited compared to the mainstream (same problem exists with plenty of other heterodox approaches to containers, like gVisor, firecracker-containerd and so on, which happened to be one of the central topics of my Bachelor thesis, so I was pretty curious about the talk and shared production experience). In other words, in addition to managing Kata, we will also need to (largely manually) do a lot of instrumentation of existing tooling (whether eBPF-based or not) due to the idiosyncracies of Kata's architecture, or write our own tooling from scratch just to reproduce a traditional monitoring/observability/tracing stack with Kata - which is in addition to managing the lifecycle of Kata itself. Still, I feel like Kata and projects building on it, like confidential containers, offer benefits that are just too exciting to be outweighted by the added layers of complexity.
